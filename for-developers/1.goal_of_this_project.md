# goal_for_this_project

## 1. 目的

適度に複雑な業務画面を題材に、**UI改善の「前後」を比較できるモック画面**を作成し、UI設計上の判断とその根拠を示す。

- 対象は UI のみ。ビジネスロジック(承認ルート、権限判定、複雑な入力チェック等)は扱わない。
- 「複雑さ」は、ルールではなく **情報量・部品の種類・操作量** から生じさせる。

## 2. 題材

架空の「カンバン式タスク管理ダッシュボード」(チームリーダー(TL)が自分含めチーム全メンバーのタスクを把握する想定。ヘッダ部 + サマリ表示 + 通知 + 可変長のカンバンボード)。

選定理由:

- 業務知識なしで用途を理解できる。
- 集計が「件数カウント」程度で済み、ロジックを排除できる。
- カード移動、インライン編集、フィルタ、通知、情報の優先度など、UI上の判断点が多い。
- 発注入力画面のような特定業務のフォーマットに寄らないため、実務の画面と目的が一致して見えることを避けられる。

実在する社内システムの画面・仕様・データは使用しない。

## 3. 成果物

| # | 成果物 | 内容 |
|---|---|---|
| 1 | 改善前モック(Before) | 素朴な実装。入力欄をテーブルに並べただけの状態 |
| 2 | 改善後モック(After) | 設計判断を適用した状態 |
| 3 | 改善ポイント一覧 | 課題 → 判断 → 効果の対応表(`specification.md` の観点に沿う) |

## 4. 達成基準

- [ ] Before / After が同一データ・同一機能で、UI以外の差がない。
- [ ] 改善ポイントごとに「どの課題に対する判断か」を1文で説明できる。
- [ ] 各改善ポイントについて、Before との差が画面上で確認できる(操作回数、視線移動、エラーの発見しやすさ等)。
- [ ] ビジネスロジックを含まない(集計はステータス別・担当者別の件数カウントのみ)。
- [ ] 説明なしで見ても、何の画面か1分以内に把握できる。

## 5. 非ゴール

- 実業務での利用、バックエンド連携、データ永続化
- 認証・認可、承認フロー
- アクセシビリティ規格への正式準拠の証明(配慮はするが、準拠判定は対象外)
- 複数画面にわたる遷移設計(1画面に限定)

## 6. 改善効果の扱い方

- 「使いやすくなった」といった抽象的な評価は書かない。
- 効果は、**操作手順数、必要なクリック数、キー操作の可否、エラー箇所の視認性**など、観察・検証できる事象で記述する。
- ユーザー調査やA/Bテストを実施していない場合は、効果を「設計上の意図」として記述し、実測値であるかのように書かない。
